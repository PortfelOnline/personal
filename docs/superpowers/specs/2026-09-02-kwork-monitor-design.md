# kwork-monitor — дизайн (черновик, работа приостановлена пользователем)

Статус: design approved by user in chat, НЕ дописан до конца (нет self-review, нет плана реализации). Продолжить с шага "spec self-review" при возобновлении.

## Задача

Агент мониторит новые заказы на kwork.ru (ниша: IT/разработка, боты, автоматизация, AI-агенты, парсинг, интеграции), уведомляет о них в отдельный Telegram-бот вместе с готовым черновиком отклика (сгенерированным через мост Code Assist), пользователь сам решает — редактировать и отправлять отклик на kwork вручную. Полного авто-отправления нет (отклик на kwork платный и необратим).

Аналогия по духу — уже существующий на `n` кейс мониторинга Telegram-чатов на релевантные запросы (вероятно, один из вертикалей GMA/get-my-agent.com, например йога-студия), но здесь источник — kwork, а не Telegram-чаты.

## Решённые вопросы (из брейнсторминга)

- **Доступ к kwork**: официального API нет, используем сохранённую cookie-сессию (как CDP-логин в audioceh/sprav).
- **Обновление сессии**: раз в N дней вручную — пользователь сам обновляет `cookies.json`, агент шлёт Telegram-алерт при протухании (403/редирект на логин).
- **Отправка отклика**: НЕ автоматом. Только уведомление + черновик, пользователь отправляет отклик на kwork сам.
- **Ниша фильтрации**: IT/разработка, боты, автоматизация, AI-агенты, парсинг, интеграции.
- **Частота проверки**: раз в 1 час (cron).
- **Контекст для генерации откликов**: да, нужен бриф о пользователе/услугах — Claude сгенерировал черновик (см. ниже), пользователь его доработает.

## Архитектура

Один Python-скрипт `kwork_watcher.py` на сервере `n` (167.86.116.15), запускается по cron раз в час. Без новых демонов/сервисов — паттерн как у существующих одноразовых cron-скриптов (`parse_watchdog.sh`, `geo_warm.py`).

### Компоненты

1. **Session store** — `cookies.json`, обновляется вручную пользователем.
2. **Fetcher** — `requests`/`httpx` с курс-кукой, тянет список заказов kwork по нужным категориям.
3. **Parser** — BeautifulSoup, вытаскивает id/title/url/description/бюджет из HTML.
4. **Dedup store** — SQLite `seen_orders.db` (id, ts) — заказ обрабатывается один раз.
5. **Proposal generator** — вызывает мост Code Assist (`codeassist-openai-shim.py`, OpenAI-совместимый эндпоинт) с system-промптом = бриф пользователя + текст заказа → черновик отклика на русском.
6. **Notifier** — отдельный Telegram-бот (токен даёт пользователь), шлёт: заголовок заказа, ссылка, бюджет, черновик отклика.
7. **Config** — `PROFILE.md` (бриф, см. ниже) + `config.yaml` (категории, интервал, пороги).

### Data flow

cron → fetch list → parse → diff vs SQLite → для новых: generate proposal via bridge → send to Telegram → mark as seen in SQLite (даже при ошибке генерации — чтобы не долбить один и тот же битый заказ; ошибка логируется отдельно).

### Обработка ошибок

- **Кука протухла** (редирект на логин/403) → Telegram-алерт «сессия протухла, обновите cookies.json», скрипт завершается без падения будущих cron-запусков.
- **Мост Code Assist недоступен** → в Telegram уходит голая ссылка на заказ без черновика + пометка «черновик не сгенерирован», остальные заказы не блокируются.
- **Верстка kwork изменилась** (парсер вернул 0 заказов там, где раньше были) → отдельный алерт «возможно сломался парсер», dedup не трогаем как «ничего нового».
- **Telegram недоступен** → лог ошибки, retry на следующем тике; dedup уже проставлен, риск разово пропустить уведомление — приемлемо для MVP.

### Тестирование

Ручной прогон `kwork_watcher.py --dry-run` — парсит и логирует в консоль, не пишет в SQLite, не шлёт в Telegram. Для проверки парсинга/генерации перед постановкой в cron.
