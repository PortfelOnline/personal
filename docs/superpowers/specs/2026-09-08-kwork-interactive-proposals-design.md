# kwork-monitor — интерактивная генерация откликов по кнопке

Статус: дизайн, подтверждён пользователем 8 сентября 2026 (архитектура), ожидает подтверждения самой спеки.

Продолжает [2026-09-02-kwork-monitor-design.md](2026-09-02-kwork-monitor-design.md) (базовый мониторинг уже реализован и в проде: PR #3, деплой на `n` в `/root/kwork-monitor`, cron каждый час в `:17`).

## Задача

Сейчас `--with-generation` — режим всё-или-ничего: либо черновик генерируется для каждого подходящего проекта в тике, либо ни для одного. Пользователь хочет сам решать по каждому уведомлению — генерировать развёрнутый отклик через ИИ или нет — нажатием кнопки в Telegram, без ручной работы с сервером.

## Решённые вопросы (из брейнсторминга)

- **Способ выбора**: inline-кнопка «Сгенерировать отклик» под каждым уведомлением о проекте.
- **Рантайм кнопки**: отдельный systemd-сервис с long polling (`getUpdates`), не часовой cron — кнопки должны реагировать сразу, а не раз в час.
- **Результат генерации**: правка того же сообщения (добавить черновик снизу, убрать кнопку) — не отдельным сообщением. Это одновременно и UX, и защита от повторной генерации на один и тот же проект.
- **Бэкенд генерации**: без изменений — тот же `ProposalClient` через уже настроенный `KWORK_CODEASSIST_BASE_URL=http://172.17.0.1:4405/v1` (шим → ViralCraft-мост :4400 → Gemini 3.x по квоте Antigravity, минуя лимиты обычного API-ключа).
- **PROFILE.md**: сейчас на сервере лежит дефолтная заглушка из `PROFILE.example.md`. Наполняется реальным стеком пользователя (см. раздел ниже) — это единственный источник фактов, которые генератор вправе использовать (system-промпт `ProposalClient` запрещает утверждать то, чего нет в проекте или профиле).

## Архитектура

### Новый компонент: `kwork_monitor/bot_daemon.py`

Постоянный процесс (systemd, `Restart=always`), отдельный от часового cron:

- Long polling `getUpdates` (`allowed_updates=["callback_query"]`), офсет апдейтов хранится в той же sqlite (`monitor_state`, ключ `telegram_offset`), чтобы рестарт сервиса не терял/не дублировал апдейты.
- На `callback_query` с `data == f"gen:{id}"`:
  1. `answerCallbackQuery` сразу (Telegram требует ответ в течение ~30с, иначе кнопка «висит» с крутилкой у пользователя).
  2. Читает строку `pending_proposals` по `id`. Если строки нет (устарела/уже обработана) — правит сообщение на «черновик уже сгенерирован или запрос устарел», кнопку убирает, выходит.
  3. Вызывает `ProposalClient.generate(project, profile)` (тот же клиент и профиль, что использует cron).
  4. `editMessageText` — дописывает черновик под существующий текст уведомления, `reply_markup` без кнопки.
  5. Если генерация упала (`ProposalError`) — правит сообщение, добавляя `⚠️ черновик не сгенерирован: <причина>`, кнопку возвращает (чтобы можно было повторить), строку `pending_proposals` НЕ удаляет.
  6. При успехе — удаляет строку `pending_proposals` (защита от повторной генерации на то же сообщение).

### Изменение cron-тика (`kwork_monitor/cli.py`, `runner.py`)

- Обычный часовой прогон (`--with-generation` не указан) теперь при уведомлении о релевантном проекте:
  1. Шлёт сообщение в Telegram с `reply_markup` — одна inline-кнопка «Сгенерировать отклик», `callback_data=f"gen:{id}"`.
  2. Сразу после успешной доставки сохраняет строку в `pending_proposals` (см. схему ниже), `id` — автоинкремент sqlite, `message_id`/`chat_id` — из ответа Telegram.
- Режим `--with-generation` (ручной, для проверки/бэкфилла) не меняется: черновик генерируется сразу в тике, кнопка не нужна, `pending_proposals` не создаётся.

### Данные: таблица `pending_proposals` в `seen_orders.db`

```sql
CREATE TABLE pending_proposals (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_url TEXT NOT NULL,
    subject TEXT NOT NULL,
    budget TEXT,
    description TEXT,
    chat_id TEXT NOT NULL,
    message_id INTEGER NOT NULL,
    created_at TEXT NOT NULL
);
```

`callback_data` = `f"gen:{id}"` — укладывается в лимит Telegram на 64 байта (id — целое число, растёт медленно: одна кнопка на один отфильтрованный проект, единицы в день).

Ретеншен: строка живёт до успешной генерации или бессрочно, если пользователь так и не нажал кнопку — по объёму это не проблема (единицы/десятки строк в месяц), отдельная чистка не нужна (YAGNI).

### Systemd-юнит

`kwork-monitor-bot.service` — `ExecStart=/root/kwork-monitor/.venv/bin/python -m kwork_monitor.bot_daemon`, `WorkingDirectory=/root/kwork-monitor`, `EnvironmentFile=/root/kwork-monitor/.env`, `Restart=always`, `User=root` (как и остальные сервисы на `n`).

## Обработка ошибок

- **Двойной клик по кнопке** (до того, как первый запрос обработан) — второй `callback_query` не найдёт строку в `pending_proposals` (если первый уже успешно завершился) или получит тот же ответ параллельно (SQLite-запись не блокирует; в худшем случае — генерация вызовется дважды, отправится две правки одного сообщения, вторая победит). Не защищаемся от гонки явно — частота кликов одного человека делает это маловероятным (YAGNI), в худшем случае — лишний вызов моста.
- **`editMessageText` упал** (например, сообщение старше 48ч и Telegram не даёт редактировать) — лог ошибки в `kwork-monitor-bot`-сервис, кнопка остаётся нажатой, но черновик не появляется. Пользователь увидит по логу; отдельный алерт не заводим (редкий край, дешевле починить руками при обнаружении).
- **Мост Code Assist недоступен на момент клика** — см. п.5 в описании демона: сообщение помечается ошибкой, кнопка возвращается для повтора.

## PROFILE.md — реальный стек

Обновляет прежний черновик из `2026-09-02-kwork-monitor-design.md` под то, что реально видно по проектам на сегодня. Пользователь проверяет на точность перед деплоем (только эти факты генератор вправе использовать):

**Позиционирование:** full-stack разработчик, специализация — автоматизация бизнес-процессов, AI-агенты и интеграции с LLM.

**Стек:** Python, PHP (7.2–7.4, legacy MVC и OpenCart), Node.js/TypeScript, Docker/Docker Compose, Nginx, MariaDB/PostgreSQL/Redis, n8n, Telegram Bot API (в т.ч. inline-клавиатуры, webhook и long polling), WhatsApp Business webhook-интеграции, LLM-интеграции (OpenAI-совместимые API, включая self-hosted мосты к Gemini/Claude), REST/webhook-интеграции с внешними сервисами, парсинг и скрапинг данных, деплой и администрирование VPS (systemd, cron, borg-бэкапы).

**Опыт (без цифр, которые нельзя подтвердить):** веду в проде несколько систем — SEO-платформа на PHP/Nginx/MariaDB/Redis с автоматизированным конвейером статей (kadastrmap.info, 100zem.ru); e-commerce на OpenCart с интеграциями фидов поставщиков и соцпубликатором (audioceh.ru); мультитенантный AI-официант на Android/iiko (aiwaiter); AI-агент для генерации и публикации контента (get-my-agent.com — WhatsApp-бот, видео-конвейер); торговый бот с сеточной стратегией на Bybit/OKX API (aitrading); n8n-автоматизации и Telegram-боты для нескольких проектов.

**Услуги:** разработка и доработка Telegram/WhatsApp-ботов и AI-агентов, автоматизация процессов на n8n, интеграция LLM в существующие продукты, парсинг и сбор данных, поддержка и рефакторинг PHP/Python-проектов, деплой и DevOps.

## Тестирование

- Юнит-тесты `bot_daemon.py`: обработка `callback_query` с существующей/несуществующей/уже обработанной строкой `pending_proposals`, ошибка `ProposalClient`, ошибка `editMessageText`.
- Юнит-тесты на изменение `runner.py`/`cli.py`: обычный тик создаёт строку `pending_proposals` и шлёт кнопку; `--with-generation` не создаёт строку и не шлёт кнопку.
- Ручная проверка на `n`: дождаться реального письма или отправить тестовое через фикстуру в боевой чат, нажать кнопку, убедиться, что сообщение поправилось и кнопка исчезла.
